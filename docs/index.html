Getting started (5 minutes)

Three steps to your first successful API call. The code panel on the right has copy-paste snippets in cURL, Python, and JavaScript for every call below.

1

Bring the lab up

Starts the Wazuh SIEM + honeypot and waits for the agent to connect. The Manager API comes up on :55000, the Indexer on :9200.

cp .env.example .env && ./start_lab.sh
2

Get an auth token

Exchange your API credentials (HTTP Basic) for a short-lived JWT. See Authentication for the full flow.

curl -k -u wazuh-wui:'MyS3cr37P450r.*-' \
  "https://localhost:55000/security/user/authenticate?raw=true"
3

Make your first call

List enrolled agents. You should see the honeypot (linux-honeypot, id 001) with status active.

curl -k -H "Authorization: Bearer $TOKEN" \
  "https://localhost:55000/agents?pretty=true"
✓
That's it. A 200 with "error": 0 and your agent in data.affected_items means you're wired up. From here, query alerts or trigger an active response.

Authentication

The Manager API uses JWT Bearer tokens. You authenticate once with HTTP Basic credentials, receive a token, then send that token on every subsequent request. Tokens expire after ~15 minutes — re-authenticate when you get a 401.

1 · Acquire credentials

Credentials are lab defaults, set in docker-compose.yml (and overridable via .env). Two separate services, two credential sets:

ServiceBase URLUsernamePassword
Manager APIhttps://localhost:55000wazuh-wuiMyS3cr37P450r.*-
Indexer APIhttps://localhost:9200adminSecretPassword
Dashboard (UI)https://localhost:8443adminSecretPassword
◆
All endpoints use self-signed TLS. Pass -k (curl), verify=False (Python), or rejectUnauthorized:false (Node) in the lab. Never disable verification against production.

2 · Exchange for a token

GET /security/user/authenticate with Basic auth returns a JWT. Add ?raw=true to get the bare token string (handy for shell variables); omit it for the JSON envelope { "data": { "token": "…" } }.

3 · Use the token

Send it as Authorization: Bearer <token> on every Manager API request. The Indexer API uses plain HTTP Basic on each call (no token step).

Automated Response (SOAR)

When Wazuh flags the brute-force, it pipes the JSON alert straight into active_defense.py on the honeypot agent. The script reads the alert from stdin, parses the attacker's srcip, and drops it with iptables — closing the kill chain automatically. The ban is appended after an ESTABLISHED-accept rule, so an existing session survives while new connections are blocked. Maps to MITRE D3FEND D3-NTF.

Malware Capture (FIM)

File Integrity Monitoring watches the honeypot's drop zones (/tmp, /home, /root) in real time. When a payload lands, the agent computes its SHA-256 and ships it in the alert; malware_capture.py — a Wazuh integration on the manager — reads that hash and queries the VirusTotal API, returning a live verdict (e.g. 65/74 engines on the EICAR test file) without the manager ever touching the file.

Threat Reporting

An offline analyst, threat_report.py, reads the Wazuh detections and asks an LLM (Gemini) to write a MITRE ATT&CK incident report — executive summary, kill-chain timeline, technique table, IOCs, severity, and recommended actions. It runs on the logs (never in the attack path), pseudonymises IOCs before egress, and rate-limits itself to stay within the free-tier quota.

Roadmap

Future: AI-Generated Honeypots

Cybersecurity is entering a phase where AI doesn't just find threats — it learns from each one and adapts in real time. AI-generated honeypots are advanced decoys that continuously evolve to lure, deceive, and analyse attackers, turning a static trap into an intelligent, self-improving defence.

◆
The problem this solves. Static honeypots (like the Docker-based one this lab ships) eventually get fingerprinted — an attacker notices there's no real filesystem, no legitimate traffic, no human behaviour — and leaves. An AI-driven honeypot instead hallucinates a convincing, ever-changing environment, keeping the attacker engaged and the intelligence flowing.

Core architecture

  • Large Language Models (LLMs). A model fine-tuned on network logs, shell commands, and attacker behaviour generates server responses, command output, and file contents with high fidelity — the "brain" that answers the attacker. LLMs are transformer networks trained on vast text corpora (e.g. GPT, Gemini) that understand context and produce fluent, relevant output.
  • Generative Adversarial Networks (GANs). Two networks — a generator and a discriminator — compete until the generator produces synthetic environments, device configs, and service banners indistinguishable from real systems, spinning up thousands of unique honeypot instances with little manual setup.
  • Prompt engineering & fine-tuning. Careful prompts and supervised fine-tuning tailor the model to specific protocols (SSH, HTTP, SMTP) and to simulate the exact vulnerabilities most likely to attract attackers.

Real-time interaction & adaptation

  • Command & response simulation. An SSH command routes to the model, which returns a context-aware response within tight latency limits — powered by optimisations like model pruning, quantisation, and parallel processing so the illusion never lags.
  • Reinforcement Learning (RL). The system is an agent in a Markov Decision Process: it observes state (attacker commands, session context), picks an action (a simulated response), and updates its policy from the reward (did the deception hold?). Over many sessions it learns to prolong engagement and extract more intelligence.
  • Dynamic environment generation. The simulated network, services, and logs are procedurally generated and mutated on the fly (new vulnerabilities, altered configs, even a changed topology), so what the attacker sees keeps changing and they can't pin down the decoy.

Operational workflow

  • Engagement. Attacker connects over a standard protocol; the honeypot presents a seemingly vulnerable system and forwards each command to the AI backend for a realistic reply.
  • Logging & behaviour analysis. Every command, response, and piece of session metadata is logged; the system identifies TTPs in real time and can predict the next move.
  • Federated learning. Distributed honeypots share anonymised threat intelligence, improving collective defence without exposing sensitive data.
  • Autonomous orchestration. Multi-agent systems manage the interaction, trigger defensive actions (deny-list updates), and write natural-language threat reports.
✓
Concrete example — an LLM-backed SSH honeypot. Attacker connects over SSH → the honeypot shows a normal login → after auth, commands like ls / ifconfig are answered by the LLM with realistic output → every interaction is logged, and RL refines the deception over time. A Python SSH wrapper (paramiko) bridges the attacker to the generative backend.

Why it matters

  • Realism & adaptability — deceives sophisticated adversaries that fingerprint static traps.
  • Scalability — automated generation deploys honeypots across many segments and devices.
  • Lower overhead — ML removes most manual configuration and maintenance.
  • Richer intelligence & fewer false positives — continuous learning surfaces emerging TTPs while filtering benign noise.
◆
This lab is the foundation. Most of what an AI honeypot needs already exists here: a real SSH honeypot, a paramiko attack harness, a SIEM ingesting every event, and Python SOAR acting on detections. The next step is to swap the static sshd for an LLM-driven shell that generates responses per command. That turns this from a detection lab into an adaptive-deception one. See docs/ROADMAP.md for the phased plan.

Error handling

All errors return a JSON body and a matching HTTP status. The Manager API uses two shapes: a simple { "title", "detail" } for auth/routing failures, and the operation envelope { "error", "data": { "failed_items": [...] } } for partial failures.

Status code map

CodeMeaningCause & fix
200OKSuccess. Still check "error": 0 and an empty failed_items.
400Bad RequestMalformed param/body. Check types and required fields.
401UnauthorizedMissing/expired token or wrong Basic creds. Re-authenticate.
403ForbiddenToken valid but the RBAC role lacks the resource.
404Not FoundUnknown endpoint or agent ID. Check the path / agents_list.
405Method Not AllowedWrong verb for the path (e.g. POST where GET is expected).
429Too Many RequestsAPI rate limit hit. Back off and retry.
500Server ErrorDaemon issue — check GET /manager/status and container logs.

Error schemas

# 401 — auth / routing failure
{ "title": "Unauthorized",
  "detail": "No authorization token provided" }

# operation with a partial failure (HTTP 200, error != 0)
{ "data": { "affected_items": [],
    "failed_items": [ { "error": { "code": 1701,
        "message": "Agent does not exist" },
      "id": ["999"] } ] },
  "error": 1 }
